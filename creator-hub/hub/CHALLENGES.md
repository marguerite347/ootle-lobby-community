# Weekly community challenge pilot

Implemented September 22, 2026. Home features the current edition; `/challenges` has its brief, submission form, three upcoming editions and twelve weeks of current/archive context. `GET /api/challenges` derives dates from the versioned bank in `server/challenges.mjs`. Each New York Monday opens the next edition, without a cron or external AI service. The page refreshes its data every minute. Week 1 is the local pilot week starting September 21, 2026, not an announced public launch. The twelve original prompts repeat in subsequent cycles. No external calendar or outbound announcement is created.

Sources checked: [series hub](https://orlandoo.itch.io/portfolio-builders-jams), [previous jams index](https://itch.io/t/5340457/previous-jams), [theme announcements](https://itch.io/t/5340459/theme-announcements), [week 92](https://itch.io/jam/portfolio-builders-jam-week-92). The previous-jams index is TODO, not a complete catalogue. Announcements list Limitless, Rebellion, Obsolete and Costume. Borrow broad optional themes, small weekly deliverables and reflection. Tari's prompts are original, tool-agnostic and AI-friendly, unlike that series' current no-AI rule. No affiliation claimed.

## Data and behavior

POST `/api/challenges/submissions` accepts editionId, creatorId, projectId, summary and HTTPS evidenceUrl, authenticated with the existing creator profile Bearer edit key. It pins the current project commit. A creator or project may enter once per edition. Closed/future editions and unsafe URL schemes are rejected. Persistence is atomic in runtime `challenge-submissions.json`; keep it out of Git and include it in the runtime backup. This local JSON store assumes one Node writer, like the current resource submission store. Move to a transactional database before multi-instance hosting.

The profile is a browser credential, not verified personhood or proof of project ownership. All entries are pending review. Counts mean submissions, not accepted work, people or paid winners. No evidence links are fetched by this service. Moderation and safe evidence inspection are separate work. No existing project was automatically entered. Test fixture submissions use temporary directories only.

## Success and reward wiring: next implementation work

1. **Versioned event publishing.** Persist each edition's prompt, target, timezone, funding and allocation rules before opening. Add organizer preview, pause, reschedule and override controls. Keep historic briefs immutable; don't edit/reorder existing bank slots. Add calendar exports and campaign links by edition ID. The current deterministic pilot is not a full editorial scheduler.
2. **Evidence review.** Add authenticated reviewer roles and a queue with accept/reject/request-changes reasons. Check exact project revision, ownership/contribution, original work, credits and demonstration. Deduplicate teams and reused evidence, retain appeals and review history. Count verified contributions only after acceptance.
3. **Outcome analytics.** Add editionId, projectId and projectRef to consented join, first successful play, Riff and return events. Measure activated builders (accepted usable release), independently reused components, actionable feedback implemented, first-session completion and seven-day returning users. Show numerators, denominators, observation windows and missing coverage. Exclude self-traffic and bots where measurable. Browser clicks and self-reported counters cannot qualify payouts.
4. **Funded community unlock.** Before a rewarded edition opens, publish its fixed budget, asset/network, eligibility window, milestone and allocation method. Initial pilot suggestion is five accepted useful contributions; this is not a validated benchmark. A milestone can unlock a community pool, with a capped base allocation per qualifying contribution and published bonuses for independently verified reuse/improvement. Do not reward raw commits, token turnover or agent run counts. Review budget and anti-abuse constraints before adopting this proposal.
5. **Payout execution.** Separate eligibility from settlement. Persist states pending-review → accepted → pool-unlocked → payout-approved → submitted → confirmed/failed. Use an idempotency key per edition/recipient/allocation, designated signing authority, receipt reconciliation, retry handling and a public aggregate payout report. Never pay from a client-side click or local save. Network/wallet, funding and approval responsibilities are not yet configured.
6. **Showcase and learning loop.** Feature accepted entries beside next week's challenge, link profiles and forkable versions, publish a recap and use measured blockers to prioritize the next prompt. Keep prompts welcoming to small projects, not volume farming.

Definition of done for reward activation: funded frozen rules, trusted review, auditable metric definitions, anti-duplicate controls, tested settlement and receipts. Current UI deliberately reports Not funded, no reward amount and no verified achievements. It does not transfer funds or claim earnings.

Validation: focused tests cover New York midnight/DST, future/closed edition rejection, unsafe evidence links, duplicate creator/project entries, exact revision capture and no automatic payout. Production UI build passes. Developer handoff: add authenticated review and immutable event publishing before enabling rewards or presenting this pilot as a public funded program.
