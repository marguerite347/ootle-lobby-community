# Lobby chat upgrade: action plan and execution instructions

Written before implementation on October 10, 2026.

## Outcome

Make the existing public Lobby conversation comfortable and familiar to Discord/Telegram users. Keep instant autogenerated guest identities, optional name changes, existing messages, the embedded sidebar, the larger `/chat` view and the current public Vercel origin. Success means two independent browser guests can converse, reply, react, see real typing, retain their place when reading history, and use the chat on a narrow mobile screen.

## Selection and reuse

- Trial and pin `@chatscope/chat-ui-kit-react` 2.1.1 and its styles 1.4.0. Reuse suitable message/group/composer primitives instead of copying a proprietary client or rebuilding a whole messaging platform. Preserve package license notices. Source: https://github.com/chatscope/chat-ui-kit-react (MIT).
- Retain the existing PostgreSQL service, server-issued guests, permissions, exact-origin checks, local drafts, typing leases, moderation and tested unread/scroll state. A UI toolkit supplies neither a messaging server nor cross-app delivery.
- Element/Matrix is a larger platform migration with a new server and identity/history work. Telegram Web A depends on Telegram services. Neither is required for this scoped upgrade.
- Existing Chat SDK adapters remain the first candidate for later authorized external connections. Do not show unconnected services as working. An always-available AI responder is a separate product integration; do not restart the bounded Grok test or fabricate participants/typing.

## Instructions to the implementing agent

1. **Establish the baseline.** Confirm repository, current main revision, clean checkout and applicable instructions. Work on a `codex/` feature branch. Preserve unrelated work. Save this complete plan before implementation. Keep private QA data, screenshots, runtime databases and credentials outside Git.
2. **Run a small component trial.** Install pinned packages with lifecycle scripts disabled. Read the actual installed APIs and relevant upstream implementation. Test safe plain-text/custom rendering, grouped messages and a composer in the actual React version before broad integration. Never pass user message HTML to a raw-HTML renderer. Record whether each reused component is installed, exercised and retained. If a component regresses accessibility, drafts or scrolling, use a smaller suitable primitive and document why; do not imply unsupported upstream behavior is verified.
3. **Build the conversation layout.** Use compact, readable message groups: repeat author/avatar only when identity, platform, day, thread context or a meaningful time gap changes. Keep unique author identities distinct even when names match. Add correct day separators, timestamps, discoverable per-message actions and safe links. Make the composer compact and growing, with Enter to send, Shift+Enter for newline, IME-safe input, send progress, preserved failed drafts and accessible names. Keep guest identity customization available without dominating the conversation.
4. **Complete the core interactions.** Preserve real typing and unread behavior. Make reply navigation and parent context clear; retrieve the selected thread independently of the recent channel window. Expose older-history loading without losing scroll position. Add a small set of real emoji reactions with identity-bound server mutations, deduplication, channel access checks and durable storage. Reactions must synchronize between guests and survive reload. Fix channel selection/pop-out URL synchronization. Show actual loading/reconnecting/offline state; do not invent online member counts or read receipts.
5. **Integrate safely.** Reuse the existing API/store patterns and private database schema. Use idempotent reaction set/unset semantics rather than ambiguous toggles. Rate-limit new mutations, enforce membership and active-account checks, and avoid leaking hidden/private messages. If a schema addition is needed, create a migration, retain backend-only RLS/grants, and apply it to the existing authorized chat database only after local tests pass. Do not read or print credential values. Update integration-gap records and generated documentation for API/storage changes.
6. **Verify locally.** Run meaningful unit/database tests for grouping across identity/day/gap boundaries, history/thread boundaries, reaction permissions/idempotency and scroll preservation. Run the existing relevant suites and build. Through CUA, use two independent local browser guests to test send/receive, reply, reactions, reload persistence, real typing/clearance, failed/offline status where supported, older-history loading, scroll/unread behavior, channel switching and pop-out. Check desktop sidebar, larger chat and a 390px mobile viewport. Inspect final pixels, keyboard access and overflow. Do not post as the user's guest identity.
7. **Capture and release.** Record the reuse decision, actual trial results, checks and limitations. Commit public source/plan/documentation, push, create and attach a PR. Run required checks; use the repository's existing owner-agent merge exception only as authorized. Merge the complete change, deploy the exact merged revision to the existing Vercel production aliases using the established CLI workflow, and verify the deployment metadata and actual served UI. A merge alone is not a deployment.
8. **Verify the public result and hand off.** Use a separate observer browser to check the new chat UI on the stable link without sending as the user. If live test posts are necessary, use a clearly identified independent test guest and keep them minimal. Confirm aliases, current revision and mobile layout. Save evidence outside Git, stop only servers created for this task, and report what is live versus remaining integration work. Never erase chat or test evidence.

## Execution record

- Pinned Chatscope 2.1.1/styles 1.4.0; npm reports no vulnerabilities. React 18 render trial verifies grouped positions, multiline escaped user content, separators and typing primitive. MIT notices are retained in the package and `/chat-notices.txt`.
- Retained plain-text textarea: upstream MessageInput uses contenteditable HTML and its Enter handler lacks our IME guard. Retained the existing tested viewport state to preserve unread semantics; reuse is explicitly limited to display primitives.
- Actual local two-guest UI trial passed: send/receive, grouping, real typing, threaded replies, escaped markup, reaction synchronization and reload persistence. 390px viewport fits without horizontal overflow and the composer uses 16px input text.
- Stopping the task-owned local service produced Reconnecting and preserved a failed-send draft. Restarting the same database restored Connected; reload retained the unsent draft.
- Loading 105 local history fixtures produced no false unread count. A new independent guest message while reading history preserved scrollTop=620 and the first visible message, showed one unread message, and Jump to latest worked.
- Remaining checks and release receipt will be appended before completion.

- Final local checks: 42 root tests, 177 client tests across 49 files, content/integration validation and full `build:site` including packaged-server runtime check passed. No dependency vulnerabilities reported. Upstream FontAwesome emits a deprecation notice; no package replacement or untested overrides were introduced.
- Browser checks cover 375/390/768/1024/1440px layouts without horizontal overflow, sidebar and full chat, separate channel/thread drafts, channel URL/pop-out agreement, and safe markup rendering. Local test messages and screenshots are outside public source.
- Applied additive `community_chat_reactions` migration to the existing authorized database. Verified RLS enabled, existing runtime DML access, one backend-only policy, and no anon/authenticated table access. No guest/provider credential values were read.
- Release-stage checklist items above are intentionally pending in this pre-release source snapshot. Exact merged commit, CI conclusion, deployment and live acceptance will be recorded in the PR release receipt and task handoff after publication.
